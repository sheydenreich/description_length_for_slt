Reading. (1) Sharp readouts: the Bayes coefficient rises from 2.3-2.4 (k/2, the smooth value) to 5.3
(k, one per decision-relevant direction) between sharpness x1 and x100, exactly the finite-n
prediction of the 1-D quadrature (reports/talk_slt/sharp_readout_1d_quadrature.txt: slope 1 per
direction before n ~ s^1.3, 1/2 after). The MAP code's 6.5 and 14.2 at x30 and x100 are therefore the
learner's own coefficient, not lambda: the plug-in pays two to three times the Bayes code for being at
the wrong place in a sharp landscape (kappa > lambda, the plan's T4 in the alignment family). Below
x10 the MAP code pays slightly less than Bayes (1.0-2.1 vs 2.4-3.0).
(2) Readable directions: the Bayes coefficient does NOT follow k/2. It is 2.0 at k = 1 (lambda_eff
0.5) and grows to 4.7 at k = 11, while the MAP code follows k/2 (0.53 ... 4.49). The directions of the
frame outside the data's (k+1)-dimensional subspace are not flat: a frame tilted by phi towards one
of them swaps cos^2(phi) of V, so the prediction moves at order phi^2 and the KL at order phi^4. They
are quartic (corrected 2026-10-22; this file first called them "curved"): Fisher and population
Hessian both vanish there, so the plug-in, whose empirical minimiser sits at zero in them for every
sample, pays nothing ((1/2) tr(F H^+) = k/2), while the Bayes code pays 1/4 per ln n for each, 1/2
for each readable one: lambda = k/2 + (11-k)/4 = 3.0, 3.25, 3.75, 4.5, 5.5. At n <= 2048 the
measured values are below that (finite n; the quartic contribution needs n c phi^4 ~ 1).
(3) Consequence for the plan's T4: kappa_MAP < lambda on smooth, deterministically constrained
families, kappa_MAP > lambda on sharp ones, kappa_OLS > lambda on reduced-rank regression; the MAP
code's slope is a learner coefficient and must be labelled as such. Figure: reports/talk_slt/
oracle_bayes_vs_map.png.

Correction (2026-10-22, review item 1.8). The d - 1 - k unreadable directions of the oracle were called
"exactly flat" (testbed docstring, write-up) and "curved but Fisher-free" (readings above). Both are wrong.
Tilting the d_V = 1 frame u by phi towards an unreadable coordinate e: the data have no e-component, so
u . (h_s - h_b) = cos(phi) dv and the readout sees v_b + cos^2(phi) dv. The prediction changes at order
phi^2 and the KL at order phi^4 (checked numerically: doubling phi multiplies the KL by 16.3-16.4 towards
e and by 4.0 towards a readable coordinate; tests/test_oracle_directions.py). A quartic direction has
learning coefficient 1/4, so the Bayes lambda of the oracle is k/2 + (d - 1 - k)/4, with multiplicity 1;
the plug-in's (1/2) tr(F H^+) = k/2 is unchanged. The sharpness sweep (d = 6, k = 5 = d - 1) has no
unreadable direction and is unaffected. The sweep records now carry "lambda_bayes".
